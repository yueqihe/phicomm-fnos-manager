# 历史数据查询优化

本说明对应当前源码。继续使用内置 SQLite，无需安装额外服务。

## 存储和查询

- 原始记录仍在 `telemetry` 表中，每台设备每分钟最多一份，保留最近 30 天。
- 一个连接负责写入，最多两个只读连接查询曲线，另一个只读连接负责完整 CSV 导出。SQLite WAL 允许读取快照期间继续写入；导出完成临时文件后释放快照，再向浏览器发送文件。
- 曲线缓存最多保存 64 项，每项最多保留一分钟。相同设备、型号、范围和数据版本的并发请求合并计算；每个请求拿到独立结果，取消一个等待请求不影响其他请求。
- 记录新增、修改和删除通过 SQLite 触发器更新数据版本，同时使所在小时的汇总失效。采集、保留期清理和外部数据导入采用同一规则。
- 24 小时曲线读取指定设备的原始记录；7 天、30 天曲线复用已完成小时的统计。首尾不完整小时读取原始记录，避免把所选范围外的读数算进去。
- 小时汇总保存数量、总和、极值和最后读数，以原始有效样本数计算平均值。用电和费用另存首末有效累计值，查询时连接相邻小时；无效读数跳过、计量归零重建基线，选中范围之前的累计值不参与计算。
- 小时汇总保存在同一数据库，重启后继续使用。首次查询旧数据时按需建立，不在启动时扫描全部历史；后续读取约 720 个小时汇总和最多两个不足一小时的原始片段。写入汇总时核对数据版本，防止覆盖同时到达的新记录。
- 过期的原始记录及小时汇总定期清理。完整 CSV 始终读取原始分钟记录，不使用汇总替代。

首次查询尚未汇总的历史仍需要读取原始记录，耗时可能接近原有查询；此后可复用已保存的汇总。磁盘和 CPU 仍由所有任务共享，独立连接消除了共用单一连接造成的排队，并不代表导出没有资源开销。

## 本机性能测试

2026-11-03，Windows AMD64，AMD Ryzen 7 8745HS。临时数据库包含 10 台模拟 S30 设备连续 30 天的分钟记录，共 432,000 条。测量单台设备最近 30 天查询，使用实际 S30 的五个计量字段，每项运行 5 次；不包含 HTTP 网络传输、浏览器绘图或首次建立汇总的耗时。

| 查询方式 | 平均每次耗时 |
| --- | --- |
| 优化前逐条读取计算 | 127.06 毫秒 |
| 复用小时汇总 | 7.82 毫秒 |
| 命中一分钟曲线缓存 | 0.18 毫秒 |

小时汇总查询约快 16 倍。以上是开发电脑上的结果，NAS 实际表现取决于 CPU、磁盘与并发负载。

复现命令：

```sh
go test ./... -run '^$' -bench '^BenchmarkHistory30Days$' -benchtime=5x -count=1
```

## 正确性验证

- 用优化前的原始查询作为对照，对五种设备逐项核对 7 天 / 30 天的所有曲线点和统计字段；覆盖小时边界、缺失时段、有效零值、无效传感器、累计值重置和跨小时费用。
- 验证记录新增、修正、删除、延迟到达、重启和保留期清理后的结果；验证过期的计算结果不能覆盖已更新的汇总。
- 并发请求、等待取消、缓存容量上限和返回结果隔离。
- 暂停完整 CSV 导出时，采集写入和新曲线查询仍可完成；只读连接不能修改数据。
- 验证旧数据库升级、完整原始 CSV、网页范围切换、曲线缺口及手机界面。

```sh
go test ./...
go vet ./...
npm run test:history
```
